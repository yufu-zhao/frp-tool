## 启动方式（本机受限环境）

- `npm run dev` 直接跑会失败：会话环境变量 `ELECTRON_RUN_AS_NODE=1` 使 Electron 以纯 Node 模式执行主进程（`app` 为 undefined）。
- 清除该变量后仍会因 Chromium 沙箱初始化失败（GPU 进程反复崩溃后 FATAL）退出，需要 `--no-sandbox`。
- 可用启动组合（不改源码）：先 `env -u ELECTRON_RUN_AS_NODE npx vite --host 127.0.0.1 --port 1854 --strictPort`，再 `env -u ELECTRON_RUN_AS_NODE VITE_DEV_SERVER_URL=http://127.0.0.1:1854 npx electron . --no-sandbox --disable-gpu-sandbox`。
- `ps`/System Events 在本沙箱受限，无法据此验证窗口，但后台任务持续 running 且无错误输出。

## SSL 证书需求方向（讨论中，未改代码）

- 用户要求按「服务端能力」分两档：A 服务端有 nginx 且可自主申请免费 SSL 证书；B 有/无 nginx 但不能自主申请（只能手动导入）。

## 方案讨论第三轮：用户给出真实硬约束（仍未改代码）

- **frps 不得长期占用 80/443；`vhostHTTPPort`/`vhostHTTPSPort` 都不能是 80/443；本机 frpc 不持有证书库；申请证书不得影响服务端 80/443 正常使用。** 已写入项目 MEMORY.md。
- 前两轮的 ①② 证书终止方案与「frps 占 80」的 HTTP-01 前提全部作废。新拓扑：访客 → 服务端 80/443 持有者（nginx 等，终止 TLS、持有证书）→ 127.0.0.1:8080 → frps → frpc → 本地 HTTP。
- 结论：DNS-01 是唯一无条件可行的验证方式；HTTP-01 需借用现有 80 持有者加精确 location 反代到 frps 高端口（要改 nginx 配置，且要求持有者是 nginx），TLS-ALPN-01 排除。
- 现有 `certificates.ts` 本机证书库 + `https2http` terminate 降级为兼容模式；启用预留的 `serverCertificateSchema`/`serverCertificates`/`renewalManager`。
- 部署分级 L0（默认，只落盘+给片段）/ L1（同路径覆盖已有证书文件，配置零改动）/ L2（独立 conf，需确认与回滚）；非 nginx 持有者强制 L0。
- 代码落点：`serverConfig()` 加端口校验、`processes.ts:280` 与 `index.ts:96` 的 httpPort===80 HTTP-01 判定需改、`frp.ts:88` httpChallenge 临时规则改走高端口、`insertHttpInclude` 弃用。
- 待用户确认：DNS 自动化程度（手动 TXT / DNS API / CNAME 委派）、默认部署级别、HTTP-01 是否保留为条件选项。

## 方案讨论第四轮：用户拍板三点（仍未改代码）

1. DNS-01 做**逐级自动化 + 手动兜底**：A1 DNS API 凭据 → A2 CNAME 委派/acme-dns → A3 复用已有 `_acme-challenge` 记录 → A4 手动 TXT（现有 `promptDnsChallenge` 可直接复用）。逐级探测、失败自动降级、级别写入证书记录、手动明确标半自动。
2. **先做只读站点检查，再由用户选自动/手动**（默认手动，自动需主动切换）。探测项：80/443 归属与进程名、`nginx -T` 的 server_name（含泛域名/正则/default_server）、ssl_certificate 路径、证书是否被多站点共用、是否面板管理。
3. **DNS-01 与 HTTP-01 两种都要**；并提出关键时序场景：服务端当前无 nginx、80/443 空闲，以后会装 nginx 占端口。
   - 已指出硬矛盾：80/443 空闲时无 TLS 终止点，HTTPS 访问链路本身不成立，证书只能「已签发·待部署」，不能假装生效。
   - HTTP-01 按 80 归属分三支：空闲→临时独立响应器绑 80（非 frps、非长期，验证完立即释放）；nginx 占用→借用其反代链路把 challenge 转到 frps 高端口 + frpc 临时规则（`frp.ts:88` 可复用）；非 nginx 占用→禁用降级 DNS-01。
   - 架构解耦：frps 永远只听固定高端口（8080/8443），nginx 是后来加的一层，frps 配置无需改动；证书实体绑定「域名+服务器」而非某台 nginx。
   - 状态机：已签发·待部署 → 待用户确认 → 已生效 → 需复核 → 回到确认；由只读探测（应用启动/SSH 连接/签发续期后/手动重测/服务端 timer 内）驱动，环境变化绝不自动改 nginx。

- 待确认收窄为：临时占用 80 是否可接受（「长期」的解释）、默认部署级别是否仍为 L0/手动、DNS API 首批支持哪些服务商。

## 方案讨论第五轮：澄清「无 nginx」场景（仍未改代码）

- 用户澄清：该场景是**全新服务器、未安装任何软件**。希望工具**临时建立 nginx 服务**，并能**随时一键卸载、清除所有相关内容**，且**不影响服务器日后正常安装使用 nginx 等软件**。

- 隔离边界：系统区绝不触碰（/etc/nginx、nginx.service、包数据库、系统日志、用户/组、PATH、sudoers、持久防火墙规则）；托管区全部在 `~/.local/share/intranet-frp/tls-proxy/`，独立 prefix/pid/日志/证书/unit 名。
- 一键卸载=清单驱动（state.json 记录所有创建资源，逆序清理、只删带标记且未改动项、快照对比、可重试），并分「停止让位」与「完全卸载」两种粒度。
- 让位：检测到系统 nginx 出现即主动提示停止托管实例、释放端口、迁移证书与反代配置，避免端口冲突。
- 选型待用户定：A 独立目录跑官方 nginx 解包二进制（跨发行版依赖是主要工程坑）vs B 自带单文件静态 TLS 反代（隔离最彻底）；系统包安装与 Docker 已排除。

## 本机证书闭环（用户「继续」后完成）

- 目标：把「80/443 空闲 → frps 直接监听 80/443 → 证书落本机 → frpc 终止 HTTPS」从签发引擎接到 frpc 实际启动，形成闭环。

## 纠正误报：服务器上没有 frps 却出现「frps (PID xxx)」

- 用户实测确认服务端未安装 frps。根因：`searchFrpsServices()` 最后的 `/proc/*/cmdline` 兜底用 `case "$exe $args" in *frps*)` 对整条命令行做子串匹配——执行该检测命令的 shell 自身（命令字符串含 frps）、带 frps 字样的 docker 包装/临时命令都会被匹配；JS 侧只找 `-c`、不核验二进制是否真是 frps，于是产出 PID 假候选。
- 处理：**彻底删除 `/proc` 进程扫描**，检索只来自 systemd（系统+用户级）/OpenRC/SysV 已注册服务；OpenRC/SysV 额外要求启动程序 basename 为 frps 且配置为绝对路径。`manager:'process'` 类型与移除拒绝逻辑保留作防御，但不再产生该类候选。
- 文案同步：`InstallPrecheck.existingServices` 注释、预检进度文案改「系统服务」；移除失败 hint 去掉「进程方式」引导，改为提示未注册系统服务的进程不会被检测。
- 验证：99 项单测（新增「不扫描 /proc」用例）、typecheck/format/build、Electron 冒烟、25 项安装流程 UI + 三档布局全通过。VERIFICATION.md 已同步。
- 教训：远程进程检测不要用命令行子串匹配，执行检测的 shell 自身就会命中；进程候选不能安全移除时也不该展示给用户做选择。
