## 实机反馈：阿里云 DNS-01 写入 TXT 报 QuotaExceeded.TTL

- 现象：签发时阿里云 `AddDomainRecord` 返回 HTTP 400，TTL 合法范围 600~86400。
- 根因：`dns-automation.ts` 的 `aliyunAdapter.set()` 传 `TTL: '60'`（DNSPod/Cloudflare 允许 60，阿里云不允许）。
- 修复：阿里云 TTL 改为 `'600'`（最小合法值）并加注释。typecheck + 107 单测通过。
- 注意：三家适配器 TTL 需按各自下限，不能统一成一个值；DNSPod/Cloudflare 的 60 保持不变。

## 排障：「调试启动不了」

- 现象：`npm run dev` 跑到 tsup 构建成功后就退出（exit 0），无 Vite ready、无 Electron 启动日志。
- 根因：应用有单实例锁（`index.ts` 的 `requestSingleInstanceLock`）。残留的旧 Electron 进程持有锁（Vite 服务已死、只有 CLOSED 连接），新实例的 Electron 拿不到锁立即 `app.quit()` → 触发 `dev.mjs` 的 `shutdown()` → 连带关掉刚起来的 Vite，表现为静默启动失败。
- 处理：终止残留 Electron（本项目的 `node_modules/electron/dist/Electron.app/.../Electron . --no-sandbox`，非 WorkBuddy/VSCode 的 Electron），确认 1854 无 LISTEN 后重启 dev，Vite + Electron 均常驻。
- 防复发：`scripts/dev.mjs` 在 Electron 启动 5 秒内退出时打印提示「若旧调试窗口仍在（单实例锁），请先关闭它再重新启动」。
- 排障要点：dist 的 tsup 构建成功只代表主进程编译过，不代表 dev 起来了；必须确认 1854 LISTEN + Electron 常驻。注意 `ps` 在沙箱下不可用，用 `pgrep -fl` / `lsof -nP -iTCP:1854`。

## include 优先级、探针与 loading

- 用户问重复 include 谁优先：Nginx 同名同 listen 的 server 块以先定义者为准，后定义会被忽略并 warn。我们插在 http 块开头，因此本工具配置优先；模板不设置 `default_server`，避免抢默认站点。弹窗已提示。
- 注入成功后在托管目录写 `default.conf` 哨兵：只含唯一 token 注释，不监听端口、不抢 default_server。`withNginxTransaction` 增加 `verify` 回调（写入→校验→reload→verify→失败回滚），Nginx 用 `nginx -T` 查 token，查不到直接回滚；Apache dump 能力因版本而异，查不到只提示“未确认生效”不回滚。
- `WebIncludeRecord` / `WebIncludeStatus` 增加 `probe`（path/token/ok/checkedAt/note）；服务器面板与注入弹窗显示探针状态，已注入时面板直接显示「解除」按钮，弹窗内同名。`siteConfigFileName('default')` 拒绝，避免规则覆盖探针。
- 所有相关异步按钮加按钮级 loading：注入、解除、重新检测、刷新检测、保存配置、重新生成、复制配置，文案变“中…”并禁用。

## TLS 双方案自动判定（用户确认需求）

- 用户先问「https 流量落在服务器 nginx 的 443 server 块，证书是否必须在服务器」——结论：TLS 在哪终止，证书就在哪；nginx 七层 `listen 443 ssl` 解密时证书必须在服务器，四层 stream 透传则由本机 frpc 终止、证书在本机。
- 用户最终拍板，**只有两个判定条件**：服务器有 Web 服务 + include 注入成功（注入记录 + `default.conf` 探针生效）→ 方案 A（服务器终止）；反之方案 B（本机终止）。其它因素（443 占用/多域名/stream 模块/权限）只校验提示，不参与决策。
- 用户四项确认：①沿用现有注入记录+探针判定；②签发后 cert/key 由工具写服务器注入目录，server 块引用；③DNS-01+HTTP-01 都要；④清除旧数据全新适配。
- 实现：`src/shared/tls-plan.ts` 单一判定源，`tls:plan` IPC；方案 A 证书落 `/etc/intranet-frp/sites/nginx/certs/`，生成 `listen 443 ssl` server 块写注入目录，规则切 http+`publicHttps`；方案 A 的 HTTP-01 用 `server_name` 精确匹配的临时 challenge server 块 + token 写 `/etc/intranet-frp/acme/`，签发后移除；失败全链路回滚。schema 升 4 清旧数据。
- 排障：schema 4 迁移把 `rule-editor-check` 桩 state（schema 3）的 https 规则转成 http，导致模板断言 `8443` 失败；把桩 state 改 schema 4 保留 https 规则即可。
- 用户实测方案 B 的 Vite dev 页面经 https 访问很慢：本地直连 `127.0.0.1` 秒开，判定为隧道链路问题——几百个未打包模块 × 每请求公网往返约 350ms + 浏览器 6 连接排队（14.5s 那批）。`https2http` 非元凶但使 TLS 握手跨公网；建议生产构建 + 检查 Connection ID 验证连接复用。
- 验证：123 单测、typecheck/format/build、四个 Electron 脚本全通过，三档无横向溢出。真实 SSH 部署、HTTP-01 challenge 应答留待实机。
